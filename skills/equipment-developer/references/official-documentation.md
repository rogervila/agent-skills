## Upstream Source

| Source | URL | Use |
|---|---|---|
| GitHub repository | https://github.com/rogervila/equipment | Framework package (`equipment/`), project template (`project/`), tests, website sources. |
| PyPI package | https://pypi.org/project/equipment/ | Released versions of the `equipment` package and CLI. |
| Template archive | https://github.com/rogervila/equipment/archive/refs/heads/main.zip | What `equipment new` downloads. |

> `equipment new` always downloads the template from the `main` branch, whatever package version is installed. A generated project can therefore contain template changes that are newer than the installed package and newer than an older docs snapshot. Read the generated files instead of assuming they match an example.

## Equipment 1.4.0

The 1.4.0 release added FastMCP to the generated project template. At the release tag, the template includes `mcpserver.py`, `config/mcp.yaml`, and `tests/test_mcpserver.py`, with `fastmcp>=4.1.7,<5` in project dependencies. This is template integration; the installed `equipment` package does not provide an MCP server API. The release also documents Python 3.15 support and raises several dependency minimums. Existing 1.3.0 runtime probes have not been re-run across every 1.4.0 dependency combination. See `references/mcp.md` for current behavior and safety notes.

## Inspecting The Installed Source

The framework layer is small (about 20 modules). When exact behavior matters, read the installed code instead of guessing:

```bash
python -m pip show equipment
python -c "import equipment, os; print(os.path.dirname(equipment.__file__))"
```

| Module | Contains |
|---|---|
| `equipment/__init__.py` | `Equipment` container, `Equipment.make()`, `equipment()`, `cli()` |
| `equipment/Command/` | Click CLI, `NewProjectCommand`, `CompileCommand` |
| `equipment/Database/SQLAlchemyFactory.py` | URL building, `engine`, `session()`, `text()` |
| `equipment/Log/` | `AbstractLogger`, `LoggerFactory`, `NullLogger` |
| `equipment/Queue/` | `AbstractQueue`, `QueueFactory`, `SyncQueue`, `RedisQueue` |
| `equipment/Scheduler/` | `AbstractScheduler`, `Scheduler` loop |
| `equipment/Storage/` | `AbstractStorage`, `StorageFactory`, `LocalStorage`, `S3Storage` |

## Source-Of-Truth Rules

Apply these rules in order:

1. The user's project files. A generated project is owned by the user and is often customized. Read `app/__init__.py`, `config/*`, `.env.example`, entry points, and `tests/TestCase.py` before advising.
2. The installed `equipment` package source, for what the code actually does at runtime.
3. This skill's verified behavior notes in `references/verified-behavior.md`, for known gaps between docs and code. They are dated evidence; re-check them when the installed versions differ.
4. The hosted docs, for intended usage, conventions, and constraints.

When the docs and the code disagree, say so explicitly. Follow the code for "what happens", follow the docs for "what is intended", and recommend the smallest change that makes the project behave as intended.

## Best Practices

- Fetch `llms-full.txt` once per session before broad Equipment work, and fetch single `.md` pages for focused questions.
- Link the exact human docs page in user-facing answers.
- Check the installed version with `python -m pip show equipment` before citing version-specific behavior.
- Read generated project files before assuming they match docs examples, because the template comes from the `main` branch.
- Treat this skill's verified notes as dated evidence. Re-check them after Equipment upgrades.
- The MCP guidance is source-checked against the 1.4.0 template and current hosted docs; it is not a local integration test of every transport or client.
